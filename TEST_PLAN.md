# Матриця тестових сценаріїв QTable

Обрано **Напрям 1 (власний Backend + Frontend)**, реалізовано рівні 1, 2, 3. Усі UI-сценарії виконуються Playwright через дії користувача. API використовується для валідації, авторизації та підготовки даних.

## Рівень 1 — перегляд групового замовлення

| ID | Тип | Сценарій | Очікуваний результат |
| --- | --- | --- | --- |
| L1-01 | Позитивний E2E | Owner створює зустріч, два гості приєднуються, один додає страви | Усі учасники видно, Draft і порожній кошик відображаються, сума правильна |
| L1-02 | Позитивний E2E | Гість змінює кількість страв | Загальна сума Owner перераховується після оновлення |
| L1-03 | Додаткова функція | Owner експортує замовлення, навіть якщо кошик порожній | Завантажується коректний UTF-8 CSV із загальною сумою |
| L1-04 | Позитивний E2E | Фільтр, сортування, пошук, відкриття деталей страви | Результати відповідають умовам |
| L1-05 | Негативний API | Список намагаються відкрити гість, інший клієнт, офіціант, анонім; невідома група/страва | 403, 401, 404 відповідно |

## Рівень 2 — підтвердження консолідованого pre-order

| ID | Тип | Сценарій | Очікуваний результат |
| --- | --- | --- | --- |
| L2-01 | Позитивний E2E | Owner і гість підтверджують кошики з однаковими стравами; третій гість залишає Draft; Owner надсилає | Однакові страви агрегуються, Draft не враховано, статус Submitted, офіціант бачить правильні позиції |
| L2-02 | Негативний E2E | Жодного підтвердженого кошика | Зрозуміла помилка, замовлення не створене |
| L2-03 | Негативний E2E | Є підтверджений порожній кошик | Помилка, замовлення не створене |
| L2-04 | Позитивний E2E | Розблокування вже підтвердженого кошика, зміна позицій | Сума та індикатор готовності оновлюються, потрібне повторне підтвердження |
| L2-05 | Негативний API | Повторний submit, гість, анонім, невідома група, редагування після submit | 409, 403, 401, 404 відповідно |

## Рівень 3 — видалення учасників

| ID | Тип | Сценарій | Очікуваний результат |
| --- | --- | --- | --- |
| L3-01 | Позитивний E2E | Owner видаляє гостя з підтвердженим кошиком | Інші гості залишаються, загальна сума зменшується |
| L3-02 | Позитивний E2E | Owner видаляє одного гостя, надсилає замовлення | Офіціант не бачить вилучених страв |
| L3-03 | Позитивний/негативний API | Видалення останнього гостя, спроба видалити Owner чи повторно видалити гостя | Лишається Owner і total=0; для Owner 400, для відсутнього гостя 404 |
| L3-04 | Негативний API | Чужа група, чужий учасник, не-Owner, анонім, неіснуючий учасник | 400, 403, 401, 404 |

## API і валідація — 16 незалежних тестів

- Границі імені: 1, 2, 50, 51 символ; дозволені дефіс, апостроф; заборонені кирилиця й цифри.
- Границі пароля: 7, 8, 16, 17 символів.
- Некоректний email (у т.ч. понад 254 символи), прізвище, підтвердження пароля.
- Повторна реєстрація, правильний і неправильний вхід, logout з інвалідацією сесії.
- Мінімум 15 хв до початку бронювання (перевірки на 14 та 16 хв), невідома локація, відсутня авторизація.
- Невідомий тип сортування, фільтр і некоректні кількості в кошику.

## Ізоляція та докази

Кожний тест запускає окремий HTTP-сервер зі своєю тимчасовою SQLite-БД і випадковим TCP-портом. Нові акаунти отримують унікальні email; дати генеруються від поточного часу. Playwright використовує окремі Browser Context для Owner, Guest та Waiter. По завершенню тесту сервер зупиняється і тимчасова БД видаляється pytest.

При падінні тесту в `artifacts/` з'являються **повноекранний скриншот і Playwright trace.zip** для кожного актора. Завжди створюються `report.html` і (якщо увімкнути аргумент) `junit.xml`.
