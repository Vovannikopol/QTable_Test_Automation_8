# QTable · Групові замовлення в ресторані

**Домашнє завдання Test Automation #8 | Напрям 1 | Рівні 🟢 1 + 🔵 2 + 🟣 3**

**Архітектура автоматизації:** Page Object Model + `pytest` + Python Playwright для наскрізних UI-сценаріїв, `requests` для API-авторизації та валідації. Проєкт створено **з нуля** — архів `marathon2026-main.zip` використано тільки як приклад вимог, до складу QTable він не входить.

![Головна сторінка QTable](docs/preview-home.png)

![Групове замовлення QTable](docs/preview-group.png)

**QTable** — власний повнофункціональний навчальний застосунок для спільного pre-order у ресторані. Backend — FastAPI + SQLite, frontend — HTML/CSS/JavaScript без складного білду. Всі користувацькі дії працюють через справжній REST API.

## Що вже реалізовано

- Реєстрація, вхід, вихід; роль **customer** для нових користувачів; роль **waiter** лише для спеціально створеного облікового запису.
- Меню (8 страв) із пошуком українською, фільтрами, сортуванням та окремою карткою страви.
- Власник (**Owner**) створює зустріч у Дніпрі, Києві або Львові та отримує 7-символьний код запрошення.
- Гості входять у свої акаунти, приєднуються до зустрічі й формують **власні кошики**.
- Owner бачить усіх учасників, склад кошиків, суму кожного та загальну суму — навіть для Draft або порожнього кошика.
- Кошик можна **підтвердити** і знову відкрити для змін; Owner має власний кошик.
- Owner надсилає лише підтверджені непорожні кошики: однакові страви об'єднуються, бронювання стає `Submitted`, замовлення — `SubmittedByCustomer`.
- Офіціант своєї локації бачить підтверджене консолідоване замовлення.
- Owner може **видалити гостя** до надсилання — сума автоматично перераховується.
- **Додаткова власна функція:** експорт поіменного групового замовлення у файл **CSV** українською (Excel-сумісний UTF-8 BOM).
- Адаптивний інтерфейс для смартфона та комп'ютера.

## 1. Запуск застосунку

**Найпростіше у Windows:** розпакуйте архів, двічі натисніть `START_WINDOWS.bat` і відкрийте `http://127.0.0.1:8000`. Перший запуск встановить необхідні бібліотеки. Для автоматизації можна окремо запустити `RUN_TESTS_WINDOWS.bat`.

Потрібен **Python 3.11+**. На Windows відкрийте термінал у папці проєкту. На Linux/macOS замість `.venv\\Scripts\\activate` виконайте `source .venv/bin/activate`.

```powershell
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Відкрийте **http://127.0.0.1:8000**. Для перегляду API Swagger: **http://127.0.0.1:8000/docs**. Дані за замовчуванням зберігаються у `instance/qtable.sqlite3` (цей файл не комітиться в Git).

Для демонстрації панелі офіціанта перед запуском сервера можна увімкнути тестового офіціанта:

```powershell
$env:SEED_DEMO_WAITER="1"
python -m uvicorn app.main:app --reload
```

Тоді доступний окремий акаунт: **`waiter@qtable.demo` / `Waiter123!`** (лише локальна демоверсія; **не вмикайте у публічному середовищі**). У CI демоофіціант створюється в тимчасовій БД для кожного тесту.

## 2. Автоматизовані E2E-тести

Установка залежностей і браузера Playwright:

```powershell
python -m pip install -r requirements-dev.txt
python -m playwright install chromium
```

Запуск **усіх тестів**:

```powershell
python -m pytest -v --junitxml=artifacts/junit.xml
```

Запуск **окремого рівня / підмножини**:

```powershell
python -m pytest -m level1 -v
python -m pytest -m level2 -v
python -m pytest -m level3 -v
python -m pytest -m api -v
python -m pytest tests/test_level2.py -k "submit" -v
```

### Які звіти створюються

| Файл | Призначення |
| --- | --- |
| `artifacts/report.html` | Автоматично створюваний HTML-звіт із результатами |
| `artifacts/junit.xml` | JUnit XML для CI (`--junitxml` у команді) |
| `artifacts/*_actorN.png` | Повноекранні скриншоти після падіння тесту |
| `artifacts/*_actorN.zip` | Playwright trace зі скриншотами, діями й DOM |

Відкрити trace: `python -m playwright show-trace artifacts/<назва>.zip`.

**Незалежність:** у кожного тесту свій сервер, власна тимчасова SQLite-БД та випадковий порт. Browser Context для Owner, Guest, Waiter ізольовані. Тести не залежать від порядку й можуть виконуватися паралельно (`pytest -n 4` після встановлення `pytest-xdist`). Мітки `level1`, `level2`, `level3`, `api` описані в `pytest.ini`.

> **Примітка про локальну перевірку:** у середовищі підготовки Chromium забороняв перехід навіть на `localhost` адміністративною політикою. Тому функціональні сценарії тут перевірено з допоміжним режимом `QTABLE_VIRTUAL_BROWSER=1`, який запускає справжній JavaScript UI в Playwright і переадресовує його HTTP-запити до справжнього ізольованого FastAPI. У звичайній системі та в **GitHub Actions** цей режим не встановлюється — браузер відкриває сайт за HTTP звичайним способом. Це **не є доказом запуску звичайного браузерного режиму локально**.

## 3. GitHub Actions — готовий хмарний пайплайн

Після публікації репозиторію workflow `.github/workflows/e2e.yml` запускається на `push`, `pull_request` та вручну (`Actions → QTable E2E and API tests → Run workflow`).

- Чотири незалежні задачі: `level1`, `level2`, `level3`, `api`.
- Установлення Python і Playwright Chromium на GitHub-hosted runner.
- Всі тести кожної групи відпрацьовують без `--maxfail`; `fail-fast: false` не скасовує інші задачі, якщо одна падає.
- **Навіть при падінні** через `if: always()` завантажуються HTML/JUnit-звіти, скриншоти та Playwright trace як артефакти GitHub Actions (14 днів).
- Падіння тестів позначає задачу як невдалу — звіти при цьому не втрачаються.

**Бонус із зірочкою:** GitHub Actions є хмарним CI-пайплайном, але інтеграцію з **ReportPortal** у цей варіант не додано, тож весь бонус не заявляється як виконаний.

## 5. Як розгорнути сайт публічно (необов'язково для здачі)

У репозиторії є `Dockerfile` та `render.yaml`. Після публікації коду відкрийте [Render Dashboard](https://dashboard.render.com/), оберіть **New → Blueprint**, дайте Render доступ до свого GitHub-репозиторію та підтвердьте створення web service. Render збере Docker-образ та запускатиме FastAPI й frontend як один вебсайт, видавши **реальну URL** у налаштуваннях сервісу. `SEED_DEMO_WAITER=0` для публічного запуску.

**Увага:** SQLite у файловій системі без постійного диска не зберігає дані після певних перезапусків/деплоїв на деяких хмарних тарифах. Для тривалого публічного використання додайте постійне сховище або перенесіть DB на керовану БД. Цей проєкт — навчальний демонстраційний сервіс; публічний деплой вручну не створювався (не було доступу до GitHub/Render користувача).

Локальний Docker:

```bash
docker build -t qtable .
docker run --rm -p 8000:8000 qtable
```

## 6. Обрані правила для неоднозначних випадків

- **Підтвердження порожнього кошика** дозволене, але групу не можна надсилати, якщо в підтверджених кошиках немає жодної страви — HTTP 400.
- **Повторне підтвердження групи** — HTTP 409, зміни після Submit заборонено.
- **Не-Owner** (у тому числі офіціант) не бачить повну групу, не підтверджує і не видаляє учасників — HTTP 403. Анонім — 401. Неіснуюча група — 404 (для авторизованого користувача).
- **Видалення останнього гостя** залишає у групі власника; якщо його кошик порожній, `total=0`. Owner не може видалити самого себе — 400. Неіснуючий учасник — 404. Учасник іншої групи — 400.
- **Замовлення (order)** створюється транзакційно **під час успішного Submit**, тобто не вимагає окремої попередньої чернетки order. Для неіснуючої групи — 404. До Submit офіціант не бачить замовлення.
- **Лише кошики `Confirmed`** включаються в `SubmittedByCustomer`. Draft-кошики показуються в списку та загальній сумі Owner, але не в підсумковому замовленні ресторану.
- **Підтверджений кошик** блокується для змін, доки користувач не натисне «Відкрити для редагування».
- Для місць у групі немає обмеження на кількість запрошених. Зустріч має дату мінімум через 15 хвилин; локація офіціанта обмежує видимість замовлень.
